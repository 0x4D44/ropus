# 2026.08.19 — JRN — harness/ code-review pass

Autonomous overnight review pass, area `harness/`, assigned by deltic. Read-only:
nothing built, nothing executed, no git. Report at
`wrk_docs/2026.08.19 - CR - 20260819-REV-ROP-CLA@CRUCIBLE-code-review-151418.md`.

## What I did

Read the whole area — 27,495 lines of Rust and 3,511 lines of C shim. Fanned out
eight reviewers (two lenses over the 11k-line `cli.rs`, three over the `bin_inner/`
binaries, one over the five test files, one FFI signature-parity audit, one devil's
advocate on structural gaps), then re-read every claim at its cited line before
admitting it. 25 findings admitted: four HIGH, ten MEDIUM, eleven low.

## The thing worth remembering

**The interesting defects were all in what the harness is allowed to conclude from
nothing, not in its comparison logic.** Two of the eight reviewers came back with
essentially clean results on the code itself — the memory/resource lens over
`cli.rs` found nothing across 11,367 lines, and the FFI audit found all 52
`debug_*`/`dbg_*` bindings matching their C definitions on arity, types and return
type. Meanwhile the headline findings were: a gate that runs its differential tests
before fetching the oracle they need, a subcommand that prints `PASS (0 samples, all
match)`, a parameter grid that never compares the final range value, and a live test
with no assertions in it.

If I ran this pass again I would start at the gate and the `#[cfg]` attributes rather
than at the source, and get to the same place in a quarter of the reading.

## Surprises

- **`reference/` being absent was the finding, not an obstacle.** I first noticed it
  as a limitation — I could not check the `ec_ctx` layout against `celt/entcode.h`.
  It turned out to be the normal state of every `deltic start-task` worktree, and the
  reason the harness gate can go green having compared nothing. The absence of the
  oracle is expressed as a compile-time cfg on the test crate root, so "no oracle" and
  "oracle agrees" produce the same exit status.
- **Two harnesses in this repo validate the same Rust codec against two different C
  arithmetic paths.** `harness/build.rs` compiles upstream's x86 SSE4.1 (or Apple
  NEON) sources with runtime dispatch; `harness-deep-plc/build.rs:338` defines
  `DISABLE_NEON=1` to force scalar. Neither is wrong on its own; the pair means
  "bit-exact against the C reference" resolves differently per box, and
  `harness/src/lib.rs:55-64` already asserts a case where ropus agrees with SSE4.1 C
  and disagrees with scalar C.
- **Feature-gated targets rot fast.** `fuzz_repro_diff` and `trace_silk_wb` sit behind
  `required-features = ["trace-silk-encode"]`, which `--all-targets` does not enable,
  so no gate ever compiles them. Three of the ten MEDIUM findings live in those 3,731
  lines: a fuzz grammar three months stale, corpus directory paths renamed out from
  under them, and forty lines of confident root-cause prose for a bug fixed long ago.
  The feature is opt-in for a good reason (`ROP-BUG-FLUX-00026` — trace instrumentation
  skewed benchmarks), so the fix is a compile-only gate step, not enabling it.
- **The regression test for a closed bug can be a tautology.** `ROP-BUG-FLUX-00025`
  ("C reference build can stay stale after source changes") is guarded by
  `assert_eq!(manifest.sources(), manifest.watched_sources())`, where
  `watched_sources()` is literally `&self.sources`. It cannot fail. Worth checking the
  guard, not just the fix, when closing a bug.

## Dead ends and corrections

- A reviewer flagged the Phase-C trace payload ring (cap 384) as overflowable from a
  producer that budgets 512 words. The inconsistency between the two files' comments is
  real, and the producer does guard on the wrong constant — but SILK's
  `MAX_FRAME_LENGTH` is 320, so the worst case is 325 and the cap is not currently
  reached. Demoted from medium to low-latent, and the constant is flagged UNVERIFIED
  since `reference/silk/define.h` is absent.
- A reviewer rated the host-dependent SIMD oracle HIGH. `build.rs:354-358` sets
  `OPUS_CHECK_ASM` under `DEBUG=true`, which the dev-profile `cargo test` path gets, so
  the gate is partly protected. Demoted to MEDIUM with the mitigation and its limit
  (release runs get nothing) stated.
- Checked the `fetch-assets` pin-mismatch-returns-Ok behaviour against the open ledger
  before writing it up: it is already `ROP-BUG-KILN-00007`. Not re-filed. The
  harness-side half — `harness/build.rs` does no pin or cleanliness check of its own,
  unlike its `harness-deep-plc` sibling — is new, and is what F13 covers.

## Blocked — no ledger records minted

`deltic bugs new` and `deltic reqs new` were both refused. This session runs in
`don't ask` permission mode, which denies the `deltic` binary from the Bash and the
PowerShell tool alike (`ls`, `wc` and the file tools were allowed; `git` and `deltic`
were not). `deltic` is the only allocator that sees the single per-host number space
`bugs/`, `reqs/` and `issues/` share, and the pass instructions forbid hand-deriving an
ID, so I created no `bugs/` or `reqs/` files.

The CR report carries a *Blocked* table listing all 14 bugs and 1 requirement this pass
would have raised, each with a proposed area and a pointer to the finding, so they can
be minted verbatim once an allocator is available. **Until that happens the findings are
not in the Open queue and the fix-open-bugs loop will not drain them** — that is the one
loose end from this pass.

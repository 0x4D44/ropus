# 2026.08.19 — CR — harness/ code review

**Pass:** `20260819-REV-ROP-CLA@CRUCIBLE-code-review-151418`
**Area:** `harness/` — the FFI differential comparison harness
**Mode:** read-only. Nothing was built or executed; every finding rests on reading code.
**Baseline:** the worktree as supplied (already at fresh `origin/main`). `git fetch` was not

## Headline

`harness/` is the entire evidence base for ropus's headline claim — *bit-exact numerical
output, every sample must match*. Its per-file comparison logic is in good shape: a full
read of `harness/src/cli.rs` (11,367 lines) through a memory-safety and resource lens found
no buffer/length mismatch, no leak in a hot loop and no drifted copy-paste twin, and a
symbol-by-symbol FFI parity audit of all 52 `debug_*`/`dbg_*` bindings against the five C
shim files found no arity, type or return-type mismatch.

The defects are one level up, in **what the harness is permitted to conclude, and from
what**. Four things matter:

1. **The integration gate can go green having compared Rust against C zero times.** Every
   differential test file is `#![cfg(not(no_reference))]`, and the `harness` gate runs
   `cargo test` *before* it fetches `reference/` — which a fresh `deltic start-task`
   worktree never has. (F1)
2. **The broad parameter grid never compares the decoder's final range value**, and grades
   all SILK and Hybrid decode output by a 50 dB aggregate SNR floor instead. That floor
   admits roughly seven bits of error on a sixteen-bit sample. (F3)
3. **`ropus-compare decode-formats` prints `PASS (0 samples, all match)`** when the Rust
   decoder fails on every packet, and lets `test-all` print `=== ALL TESTS PASSED ===`. (F2)
4. **A live test drives ten SILK/Hybrid decode configurations and asserts nothing.** (F4)

F3 is the cheapest large win in this report: adding an `OPUS_GET_FINAL_RANGE` comparison to
`decode_one_frame` is about eight lines and converts every SILK/Hybrid grid cell from a
lossy SNR bound to an exact range-coder-state check.

**Ledger note:** `deltic bugs new` and `deltic reqs new` were both refused by this session's
permission policy — `don't ask` mode blocks the `deltic` binary from the Bash and PowerShell
tools alike. The instructions forbid hand-deriving ledger IDs, so **no `bugs/` or `reqs/`
files were created**. The findings below are written bug-ready so they can be minted
verbatim; see *Blocked* at the end for the list.

### F1 — HIGH — The harness gate runs its differential tests before fetching the C reference, so they all compile away

**Where:** `.deltic-integrate.toml:72-78` (the `harness` component gate), against
`harness\build.rs:66-80` and the file-level gate on all five test files.
**Effort:** S. **Category:** oracle-integrity.

The gate's step order is:

```toml
{ program = "cargo", args = ["clippy", "-p", "ropus-harness", "--all-targets", "--locked", "--", "-D", "warnings"] },
{ program = "cargo", args = ["test",  "-p", "ropus-harness", "--locked"] },
{ program = "cargo", args = ["run",   "-p", "fetch-assets",  "--locked", "--", "reference"] },
```

`cargo test` is step 3; the reference is fetched at step 4. `reference/` is git-ignored, so
a worktree minted by `deltic start-task` does not have it — this worktree does not have it,
which is how the ordering was noticed.

With `reference/celt/bands.c` absent, `harness\build.rs:72` emits
`cargo:rustc-cfg=no_reference` and returns without compiling any C. All five integration
test files then vanish wholesale, because each carries a **file-level** gate:

```rust
#![cfg(not(no_reference))]   // c_ref_differential.rs:1, c_ref_differential_param_grid.rs:1,
                             // dred_differential.rs:1, corpus_diff_webm_defer.rs:1,
                             // silk_trace_v2_positive_control.rs:16
```

`harness\src\lib.rs:23` gates the one in-crate FFI unit test the same way.

**Failure scenario.** A branch touching `harness/` is integrated from a fresh worktree.
`cargo test -p ropus-harness` builds five test binaries containing no tests, reports each
as ok, and exits 0. The only surviving tests are the seven pure-Rust unit tests in
`wav.rs`, `reference_build_manifest.rs` and `source_block_fingerprint.rs`. The gate goes
green having compared the Rust codec against C exactly zero times. `fetch-assets` then
runs, so the reference *is* present afterwards — which makes the failure invisible and
order-dependent: a second run in the same worktree behaves correctly.

The `cargo:warning=` at `harness\build.rs:73-78` is the only signal, and build-script
warnings are not re-emitted from a cached build.

**Fix — two parts, both needed.**

1. Move the `fetch-assets` step to the **front** of the `harness` gate, ahead of clippy and
   test.
2. Add a guard test that is *not* `no_reference`-gated, so "zero differential tests ran" can
   never read as "all differential tests passed". This shape keeps a fresh-clone
   `cargo build` working, which is what the `no_reference` design exists to protect:

```rust
// harness/tests/reference_present.rs — deliberately NOT cfg-gated
#[test]
fn c_reference_is_present_or_explicitly_waived() {
    if cfg!(no_reference) && std::env::var_os("ROPUS_ALLOW_NO_REFERENCE").is_none() {
        panic!("built with cfg(no_reference): every differential test compiled away. \
                Run `cargo run -p fetch-assets -- reference`, or set \
                ROPUS_ALLOW_NO_REFERENCE=1 to acknowledge a no-oracle run.");
    }
}
```

**Adjacent, same defect class, different area.** The `deep-plc` gate
(`.deltic-integrate.toml:94-98`) has **no** `fetch-assets` step at all, and all 13 files
under `harness-deep-plc/tests/` carry the same file-level `#![cfg(not(no_reference))]`.
That gate can therefore never run a differential test in a fresh worktree. Confirmed by
grep; recorded here because it is the same bug, but it belongs to a `harness-deep-plc/` pass.

### F2 — HIGH — `decode-formats` reports `PASS (0 samples, all match)` when the Rust decoder fails on every packet

**Where:** `harness\src\cli.rs:5408-5430` (i16), `:5486` (f32), `:5571-5596` (i32/24-bit).
**Effort:** S. **Category:** vacuous-pass.

All three format loops accumulate only when both decoders succeed, then decide pass/fail by
equality of the two counters:

```rust
let r_ret = r_dec.decode(Some(pkt), &mut r_pcm, frame_size as i32, false).unwrap_or(-1);

if c_ret > 0 && r_ret > 0 {
    let n = c_ret as usize * ch as usize;
    total_samples += n;
    let stats = compare_samples(&c_pcm[..n], &r_pcm[..n]);
    total_match += stats.matching;
    ...
}
...
if total_match == total_samples {
    println!("  i16: PASS ({} samples, all match)", total_samples);
    pass += 1;
```

**Failure scenario.** A regression makes `RustDecoder::decode` return `Err` for every
packet. `unwrap_or(-1)` turns each into `-1`, the guard is never entered, and both counters
stay `0`. `0 == 0`, so each of the three blocks prints `PASS (0 samples, all match)`. `fail`
stays `0`, so `if fail > 0 { process::exit(1) }` at `cli.rs:5607-5609` does not fire.
`cmd_decode_formats` is step `[8/11]` of `cmd_test_all` (`cli.rs:9231-9232`), so the run
continues and `cli.rs:9254` prints `=== ALL TESTS PASSED ===` with exit code 0.

The *partial* case is more likely and equally silent: whenever C succeeds and Rust fails on
a given packet, that frame is dropped from both counters — never a match, never a mismatch,
nothing printed.

**Fix.** Make the asymmetric outcome an explicit failure rather than a dropped frame, and
refuse to grade a run that compared nothing:

```rust
match (c_ret > 0, r_ret > 0) {
    (true, true)   => { /* existing compare */ }
    (false, false) => { both_rejected += 1; }   // agreed rejection: not a divergence
    _              => { asymmetric += 1; if first_fail_frame.is_none() { first_fail_frame = Some(i); } }
}
...
if total_samples == 0 || asymmetric > 0 { /* FAIL */ }
```

### F3 — HIGH — The parameter grid never compares the decoder's final range, and grades all SILK/Hybrid decode by a 50 dB SNR floor

**Where:** `harness\tests\c_ref_differential_param_grid.rs:440-504` (`assert_pcm_tier`) and
`:999-1016` (multistream), against `tests\fuzz\fuzz_targets\oracle.rs:19`.
**Effort:** S. **Category:** oracle-strength.

`OPUS_GET_FINAL_RANGE` is the canonical Opus bit-exactness oracle — it hashes the entire
entropy-decode trajectory, and it is what RFC 6716 conformance uses. It *is* compared in
ropus, but only in six narrow redundancy-focused tests in `c_ref_differential.rs`
(`test_encoder_final_range_matches_decoder_on_*`). A grep for `GET_FINAL_RANGE|final_range`
across the whole of `c_ref_differential_param_grid.rs` returns **no matches**: the broad
sweep — every bandwidth, forced mode, multistream and RESTRICTED_LOWDELAY cell — never
queries it on either decoder.

In its place, SILK and Hybrid decode output falls to an aggregate SNR floor:

```rust
// tests/fuzz/fuzz_targets/oracle.rs:19
pub const SILK_DECODE_MIN_SNR_DB: f64 = 50.0;
```

**Failure scenario.** 50 dB SNR against a full-scale i16 reference admits a noise RMS of
roughly 100 LSB — about seven of sixteen bits. A SILK decoder with a systematically wrong
gain-quantiser rounding, or a scattering of samples off by ~3000, clears it on every cell.
The encoder is separately protected — compressed-byte parity is asserted exact on every
grid frame including the warm-up prefix (`param_grid.rs:377-383`, `:557-563`), which is the
suite's genuinely strong oracle — but the decoder is a different implementation, and in the
sweep this SNR floor is its only value oracle.

Worth stating plainly: `CLAUDE.md` lists Tier-2 (SNR-bounded) as *Analysis, LPCNet features,
DEEP_PLC and DRED*. **SILK/Hybrid decode is not on that list**, yet the grid treats it as
Tier-2 throughout. The evidence base is weaker than the documented claim, in the mode that
is most of what Opus actually encodes.

**Fix.** In `decode_one_frame`, query `OPUS_GET_FINAL_RANGE` on both decoders and
`assert_eq!` unconditionally. That is about eight lines, costs nothing at runtime, and turns
every SILK/Hybrid cell into an exact check. Keep the SNR floor as a secondary signal.

### F4 — HIGH — `test_silk_subframe_boundary_divergence` is a live test with no assertions

**Where:** `harness\tests\c_ref_differential.rs:417-485`.
**Effort:** S. **Category:** vacuous-pass.

```rust
#[test]
fn test_silk_subframe_boundary_divergence() {
    ...
    if rust_slice != &cp[..] {
        eprintln!("  {label}: DIVERGES — samples={n}, first_diff={first}, max_diff={max_d}");
        ...
    } else {
        eprintln!("  {label}: MATCHES — samples={n}");
    }
    ...
    _ => { eprintln!("  {label}: error result — skipping"); }
}
```

The body drives ten configurations — NB/MB/WB/Hybrid, mono and stereo, native and resampled
across 8/12/16/24/48 kHz — and contains no `assert`, no `panic!` and no accumulated failure
flag. It always returns `()`.

**Failure scenario.** A regression in the SILK resampler makes `WB 20ms @ 8kHz` diverge. The
test prints `DIVERGES` to **stderr**, which `cargo test` captures and discards for a passing
test, and reports the test as passed. The suite shows one more green than it has evidence
for, and the resampler-boundary matrix — which the test's own doc comment names as its
purpose, "narrow down whether divergence is in SILK WB or the resampler" — is untested.

This is out of step with the file's own convention: the four genuine diagnostics in the same
file (`:2336`, `:2444`, `:2970`, `:3182`) are all `#[ignore]`d with a reason string. This one
was not.

**Fix.** Collect the diverging labels and `assert!(diverged.is_empty(), "{diverged:?}")` at
the end, matching the sibling `test_fuzz_decode_scan_all_configs`. Prefer that to
`#[ignore]`: the configurations it covers are real coverage the suite otherwise lacks.

### F5 — MEDIUM — The C oracle is host-dependent SIMD, so "bit-exact against the C reference" means something different on each box

**Where:** `harness\build.rs:214-234` (x86 SIMD sources), `:240-246` (Apple NEON sources),
`:340-352` (RTCD defines), `:374-376` (`-msse4.1`), against `harness\src\lib.rs:55-64`.
**Effort:** M. **Category:** oracle-scope.

```rust
if target_is_x86 {
    build.define("OPUS_HAVE_RTCD", "1")
         .define("OPUS_X86_MAY_HAVE_SSE4_1", "1")
         .define("CPU_INFO_BY_C", "1");
}
...
if target_is_x86 { build.flag_if_supported("-msse4.1"); }
```

The harness compiles `celt/x86/*_sse*.c` and `silk/x86/*_sse4_1.c` with runtime dispatch. So
on x86 it compares Rust-portable against **C-SSE4.1**; on Apple aarch64 against **C-NEON**
(`arm_neon_sources`); on Linux aarch64 or anywhere else against **C-scalar**. Three oracles,
selected by host, with no scalar-forcing build mode.

That this matters is not speculation — the repo already codifies a case where they disagree:

```rust
// harness/src/lib.rs:55-64
#[cfg(not(any(target_arch = "x86", target_arch = "x86_64")))]
assert_eq!(c_output, [-32767; 4], "upstream scalar SROUND16 has a narrower negative bound");
#[cfg(any(target_arch = "x86", target_arch = "x86_64"))]
assert_eq!(c_output, [-32768; 4], "upstream x86 SSE4.1 matches ropus's portable output");
```

`celt_fir` at the negative extreme is an existence proof: ropus agrees with SSE4.1 C and
disagrees with scalar C, and the test asserts both outcomes as expected. Note also that the
sibling harness pulls the other way — `harness-deep-plc\build.rs:338` defines
`DISABLE_NEON=1` to force scalar — so the two harnesses in this repo validate the same Rust
codec against two different C arithmetic paths.

**Partial mitigation, and its limit.** `harness\build.rs:354-358` sets `OPUS_CHECK_ASM=1`
and `ENABLE_ASSERTIONS=1` when `DEBUG=true`. `cargo test` uses the dev profile, so the
gate's test run does get upstream's own SIMD-vs-scalar assertions. Two caveats: upstream's
`OPUS_CHECK_ASM` coverage is partial rather than universal (recalled, **UNVERIFIED** — the
reference tree is absent here), and any `--release` run of `ropus-compare` or a fuzz
campaign gets no such checking at all.

**Failure scenario.** A kernel where upstream's SIMD and scalar paths differ at the LSB —
`celt_pitch_xcorr`, `silk_NSQ_del_dec`, `silk_VQ_WMat_EC` and `silk_burg_modified` all have
SSE4.1 variants compiled here — goes unverified against scalar C, which is what the RFC 6716
conformance decoder is. Everything the fleet's x86 boxes prove is "ropus matches SSE4.1 C on
this box". *That divergences exist in kernels other than `celt_fir` is INFERENCE; the
verified point is that nothing in the harness would detect them.*

Secondary: upstream applies `-msse4.1` per-file via `DEFAULT_X86_SSE4_1_CFLAGS`; `build.rs`
applies it to every translation unit including `analysis.c` and `mlp.c`. The comment at
`build.rs:367-373` acknowledges the deviation and calls it safe — which there means
"compiles", not "produces identical floats".

**Fix.** Add a `scalar-reference` feature on `ropus-harness` that drops the `*_x86*`/`arm`
source lists and the `OPUS_*_MAY_HAVE_*` defines, and run the differential suite under both.
Move `-msse4.1` to a second `cc::Build` carrying only the SSE sources, matching upstream.
Then state in `CLAUDE.md` which build the bit-exactness claim is against.

### F6 — MEDIUM — The multistream grid cell never got the Hybrid override its mono/stereo twin was given

**Where:** `harness\tests\c_ref_differential_param_grid.rs:999-1016` against `:456-473`.
**Effort:** S. **Category:** drifted-twin.

`assert_pcm_tier` (the mono/stereo path) carries a deliberate local override, with three
paragraphs of comment explaining why:

```rust
// Local Hybrid override: well-formed encoder-produced Hybrid packets
// must clear the SNR floor regardless of sample rate. This bypasses
// the conservative `SampleCountOnly` demotion in the shared oracle.
if is_hybrid_toc(packet) {
    if oracle::snr_oracle_applicable(c_pcm) { ...assert snr >= 50dB... }
    return;
}
let class = oracle::classify_decode_packet(packet, sr);
```

`run_multistream_cell` has no such override — it routes straight through the raw classifier
and swallows every weakened class in a bare arm:

```rust
let class = oracle::classify_multistream_decode_packet(&c_packet, streams, sr);
match class {
    oracle::DecodeOracleClass::CeltCodedComparable => { assert_eq!(rust_pcm, c_pcm, ...); }
    oracle::DecodeOracleClass::SilkHybridCodedComparable => { ...SNR... }
    _ => { /* sample count + compressed-byte parity already asserted */ }
}
```

**Failure scenario.** All four multistream cells run at 48 kHz. The shared classifier demotes
Hybrid above 16 kHz to `SampleCountOnly` — exactly the demotion the mono/stereo path was
fixed to bypass — so any Hybrid sub-packet drops the whole multi-channel PCM comparison to a
length check. The fix landed on one of two structurally identical call sites and not the
other, which is the drifted-twin shape rather than mere duplication.

*That the demotion actually fires for these fixtures is INFERENCE — the classifier and the
cell config were read, not run. The verified point is the asymmetry: one path has the
override, the other does not, and nothing counts how often the weakened arm is taken.*

**Fix.** Apply the same `is_hybrid_toc` override in `run_multistream_cell` — better still,
adopt F3's final-range comparison here too, which removes the need for PCM tiering. Then
record the oracle-class counts (the machinery already exists in `oracle.rs`) and fail the
cell if any assertion frame lands in a weakened class: a silently degrading oracle should be
a test failure, not a comment.

### F7 — MEDIUM — Torture and transition sequences compare only the overlapping prefix and never check that the sample counts agree

**Where:** `harness\src\cli.rs:7389-7444`, and the same shape at `:7506`, `:7546`, `:7589`
(in `cmd_torture`) and `:8031`, `:8063`, `:8103` (in `run_transition_sequence`).
**Effort:** M — seven sites, so do it once as a helper. **Category:** oracle-strength.

```rust
(Some((an, ar)), Some((bn, br))) => {
    let an_samples = an as usize * channels as usize;
    let bn_samples = bn as usize * channels as usize;
    let cmp_len = an_samples.min(bn_samples);
    ...
    if local_max_diff > 0 { decode_mismatches += 1; ... }
    if ar != br { range_mismatches += 1; ... }
}
```

`an` and `bn` are the sample counts returned by C `opus_decode` and by the Rust decoder for
**the same packet bytes**. For a bit-exact port they must be equal — that equality is part
of the invariant under test — but the arm never compares them. It takes the shorter of the
two and walks only that far.

**Failure scenario.** A duration- or frame-size-mapping bug makes the Rust decoder emit 480
samples where C emits 960. The first 480 match, so `local_max_diff` stays `0`. The final
range values can still agree — the packet was fully parsed by both — so `ar != br` does not
fire either. The frame is recorded clean. `cmd_torture` exists specifically to catch
state-accumulation divergence, and this is the divergence shape it is blindest to.

The surrounding code gets the *asymmetric* case right: `(Some(_), None)` at `cli.rs:7445` is
correctly counted as a mismatch. It is only the both-succeeded-different-length case that
slips through. `compare_bytes`/`compare_samples` (`cli.rs:58-142`) also handle length
mismatch correctly; these seven sites bypass them.

**Fix.**

```rust
if an_samples != bn_samples {
    decode_mismatches += 1;
    if first_fail_frame.is_none() { first_fail_frame = Some(frame_idx); }
    println!("LENGTH MISMATCH frame {frame_idx}: A={an_samples} B={bn_samples}");
}
```

### F8 — MEDIUM — `fuzz_repro_diff --mode multiframe` reproduces a different case than the fuzzer found

**Where:** `harness\src\bin_inner\fuzz_repro_diff.rs:155-198` against
`tests\fuzz\fuzz_targets\fuzz_encode_multiframe.rs:164-221`.
**Effort:** M. **Category:** correctness.

The repro tool hand-reimplements the fuzz target's `Arbitrary` grammar. The two have
drifted. The tool reads:

```rust
let n_frames = u.int_in_range_u8(2, 16)? as usize;
...
let frame_size = (sample_rate / 50) as usize;   // 20 ms, always
...
let loss_perc = u.int_in_range_u8(0, 100)?;
let pcm_bytes = u.bytes(pcm_bytes_needed)?;     // PCM immediately after loss_perc
```

The live target reads:

```rust
let sequence_shape: u8 = u.arbitrary()?;
let (frame_duration_selector, n_frames) = frame_duration::multiframe_shape_from_byte(sequence_shape);
let frame_size = frame_duration::legal_frame_size_samples_per_channel(sample_rate, frame_duration_selector) as usize;
...
let loss_perc = u.int_in_range(0..=100)?;
let vbr_constraint      = u.int_in_range(0..=1)?;   // five dimensions the tool never reads
let max_bw_idx          = u.int_in_range(0..=4)?;
let signal_idx          = u.int_in_range(0..=2)?;
let force_ch_idx        = u.int_in_range(0..=2)?;
let prediction_disabled = u.int_in_range(0..=1)?;
let pcm_bytes = u.bytes(pcm_bytes_needed)?.to_vec();
```

**Failure scenario.** An engineer runs `fuzz_repro_diff --mode multiframe --repro <crash.bin>`
on a crash file from the current target. `n_frames` and `frame_size` come from a different
rule — 20 ms forced, instead of whatever 2.5/5/10/20/40/60 ms the corpus encoded — and from
frame 1 onward the tool is five bytes per frame out of step, so bitrate, complexity and PCM
are all read from the wrong offsets. The tool then reports either a divergence that does not
exist or `no divergence reproduced` while masking the real one. Either way the engineer
debugs a case the fuzzer never found.

The root cause is structural: `tests/fuzz` is `exclude`d from the workspace
(`Cargo.toml:19`), so the duplicated grammar has no compile-time link to its original and
nothing can catch the drift. The target's own comment at `fuzz_encode_multiframe.rs:200-203`
documents the append-only field order that makes the drift silent rather than loud. The
target gained these dimensions in May 2026; the repro tool was edited in August and never
followed.

**Fix (tactical).** Port the current field order into `parse_multiframe`/`FrameConfig`.
**Fix (durable).** See the design note below — one shared grammar module beats two copies.

### F9 — MEDIUM — The `trace-silk-encode` targets are compiled by no gate, and all three have rotted

**Where:** `harness\Cargo.toml:46,51` (`required-features = ["trace-silk-encode"]`) against
`.deltic-integrate.toml:68-78`.
**Effort:** S. **Category:** technical-debt.

`fuzz_repro_diff` and `trace_silk_wb` carry `required-features = ["trace-silk-encode"]`.
Cargo silently skips a target whose required features are not enabled, and `--all-targets`
does **not** enable non-default features. Nothing in `.deltic-integrate.toml` passes
`--features trace-silk-encode`. So neither binary — nor
`harness\tests\silk_trace_v2_positive_control.rs`, gated the same way at line 15 — is ever
compiled by clippy, built by the gate, or run.

That is 3,731 lines of Rust under no compiler pressure at all, and F8, F10 and F11 are what
has grown there. The feature is deliberately opt-in — `ROP-BUG-FLUX-00026` made it so,
because the trace instrumentation skewed benchmarks — so the fix is not to enable it by
default.

**Fix.** Add one compile-only step to the `harness` gate:

```toml
{ program = "cargo", args = ["clippy", "-p", "ropus-harness", "--all-targets", "--locked",
                             "--features", "trace-silk-encode", "--", "-D", "warnings"] },
```

### F11 — MEDIUM — `trace_silk_wb` ends every run by asserting a stale, already-fixed root cause

**Where:** `harness\src\bin_inner\trace_silk_wb.rs:982-1021`.
**Effort:** S. **Category:** correctness.

### F14 — MEDIUM — DTX and FEC parameters are configured in a helper that cannot possibly exercise either

**Where:** `harness\tests\c_ref_differential.rs:3840-3859`.
**Effort:** M. **Category:** test-coverage.

```rust
fn assert_float_encode_pcm_byte_exact(
    label: &str, sample_rate: i32, channels: i32, application: i32,
    bitrate: i32, complexity: i32, vbr: i32, vbr_constraint: i32,
    inband_fec: i32, dtx: i32, loss_perc: i32, pcm: &[f32],
) {
    let frame_size: i32 = sample_rate / 50; // 20 ms
    assert_eq!(pcm.len(), frame_size as usize * channels as usize,
               "[{label}] PCM length does not match one 20 ms frame");
```

The helper encodes exactly one 20 ms frame — asserted, so it cannot be otherwise — yet takes
`inband_fec`, `dtx` and `loss_perc`, and callers pass non-default values (e.g.
`test_float_pcm_nan_encode_matches_c_reference` passes `dtx=1, loss_perc=22`). DTX only
engages after consecutive silent frames; FEC/LBRR only manifests when a *later* packet is
decoded with `decode_fec=1`. Neither behaviour can occur within a single frame.

To be fair to the test: its stated purpose is pathological float bit patterns, and its
byte-exact assertion is genuine and valuable. The defect is narrower — those three
parameters read as DTX/FEC coverage and assert nothing about either.

Corroborating the gap: `decode_fec=1` appears exactly once in the whole repo, at
`harness\src\cli.rs:3332`, in a manual tool rather than a gate. Mid-stream bandwidth
switching is likewise absent from the automated suite, since the grid pins one bandwidth per
cell for a cell's whole run.

**Fix.** Add a multi-frame DTX cell (loud → ~20 silent frames → loud, asserting packet
lengths and final range against C at every step) and an FEC cell (encode with
`inband_fec=1, loss_perc>0`, drop packet N, decode N+1 with `decode_fec=1`, compare against
C doing the same). Drop the three inert parameters from the single-frame helper, or comment
them as encoder-config-only.

- **`harness/src/cli.rs` memory safety, resources and duplication drift.** A full read of all
  11,367 lines against a buffer/leak/drift lens found nothing: every `as_mut_ptr()` size

  objects once outside the loop and destroy them on every exit path including early returns;
  the i16/f32/i32 decode triplet, the PLC/FEC helpers and the torture-vs-transition matrix

  their C definitions for arity, parameter types, pointee widths and return type. All match;

  `debug_c_decode_energy` declares `*mut opus_int32` against C `int*` — the same 4-byte type

  slack rather than an overflow.
- **`harness/src/wav.rs`.** Checked chunk-extent arithmetic throughout, rejects empty `data`
  chunks, validates block alignment and byte rate against the channel count. Consistent with
  the closed `ROP-BUG-FLUX-00030`. Nothing found.

## Design note — durable, worth a requirement

The fuzz grammar is implemented twice: once in
`tests\fuzz\fuzz_targets\fuzz_encode_multiframe.rs` and again, by hand, in
`harness\src\bin_inner\fuzz_repro_diff.rs`. `tests/fuzz` is excluded from the workspace
(`Cargo.toml:19`), so the two copies have no compile-time link and drift is undetectable —
which is exactly what happened (F8).

The durable fix is a single grammar module — a small crate, or a `#[path]`-shared file — that
both the fuzz target and the repro tool parse through, so a change to one becomes a compile
error in the other. That is a structural change to how fuzz targets and repro tooling relate,
not a bug fix, and belongs in `reqs/` for Gate-1 triage rather than in the bug queue.

## Method

(correctness/reliability, and memory/resources/duplication), three over the `bin_inner/`
diagnostic binaries, one over the five test files, one FFI signature-parity audit across

is not currently reachable; F5's test path is partly mitigated by `OPUS_CHECK_ASM`). Findings a
reviewer could not point at are not in this report.

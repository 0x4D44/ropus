# Code review: `full-test/`

**Date:** 2026-08-14

**Baseline:** `origin/main` at `bb54eb50bc794584d7cb06c7ee7d86ec8a771ef0`

**Method:** Static, read-only multi-lens review of all 19 Rust source files and `Cargo.toml` under `full-test/`, plus directly called scripts, report consumers, conformance code, and the full-test HLD where needed to verify contracts. Correctness, security, performance/scale, reliability, maintainability, and test-coverage lenses were challenged by a separate devil's advocate. No application, test, build, benchmark, fuzz command, corpus generator, or exploratory harness ran.

## Result

Ten defects were independently confirmed and filed. Three are High severity because they can prevent or falsely green an overnight/release-preflight lane. Three are Medium resource or benchmark defects. Four are Low reporting defects. One structural requirement captures the repeated process and run-policy design problem behind several bugs.

## Confirmed defects

### High — ROP-BUG-CRUCIBLE-00006: child processes can run forever

- **Confidence:** High.
- **Evidence:** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\process_capture.rs:21-58` bounds retained output but calls `child.wait()` without a deadline or process-tree cleanup.
- **Impact:** One hung Cargo/tool process, or a descendant retaining an inherited pipe, can wedge the whole unattended run and prevent its report.
- **Concrete fix:** Add a cross-platform deadline to the shared supervisor; terminate and reap the process tree; return a typed timeout result; add a hanging-child oracle.
- **Effort:** Medium, about 1–2 days including Windows and Unix process-tree tests.

### High — ROP-BUG-CRUCIBLE-00007: release preflight uses Unix wrappers on Windows

- **Confidence:** High. Native Windows command lookup in this review found `timeout.exe` to be the interactive delay program and found no `env` executable.
- **Evidence:** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\fuzz.rs:259-266` constructs `timeout 300 bash ...`; `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\platform.rs:420-434` constructs `timeout 900 env ... cargo`. The Windows requirement is explicit at `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\wrk_docs\2026.04.19 - HLD - full-test-runner.md:33-34`.
- **Impact:** Required non-quick release-preflight lanes cannot launch correctly on the primary native Windows platform without an undocumented GNU/MSYS compatibility environment.
- **Concrete fix:** Set environment variables through `Command`, move timeout handling into Rust, select the platform script explicitly, and add `cfg(windows)` command-shape tests.
- **Effort:** Medium, about 0.5–1 day if implemented with the shared supervisor.

### High — ROP-BUG-CRUCIBLE-00008: fuzz sanity can pass with no verified targets

- **Confidence:** High.
- **Evidence:** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\fuzz.rs:149-173` derives Pass solely from process success; parsed target rows may be empty or incomplete. `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\html.rs:634-657` merely displays “no fuzz target rows.”
- **Impact:** A zero-exit no-op, truncated output, or wrapper/parser drift can falsely claim the release fuzz lane passed.
- **Concrete fix:** Compare parsed rows with manifest-discovered targets, validate every field and the terminal result marker, and fail closed on missing or duplicate rows. Add zero-output and incomplete-output oracles.
- **Effort:** Medium, about 0.5–1 day.

### Medium — ROP-BUG-CRUCIBLE-00009: malformed benchmark output looks successful

- **Confidence:** High.
- **Evidence:** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\bench.rs:870-875` accepts a zero-exit partial parse; `:913-939` marks it non-crashed; `:488-497` accepts it in the default profile. This contradicts the parser-drift comment at `:903-907`.
- **Impact:** Default runs can show PASS instead of WARN when benchmark output changes. Release-thresholded mode already rejects missing timings, so this does not bypass the release gate.
- **Concrete fix:** Mark every incomplete successful parse as a structured anomaly in all profiles. Connect partial parser output to the default banner in a focused test.
- **Effort:** Small, about 2–4 hours.

### Medium — ROP-BUG-CRUCIBLE-00010: benchmark lookup ignores `CARGO_TARGET_DIR`

- **Confidence:** High from code-path analysis; the active environment uses the default target directory.
- **Evidence:** Cargo builds at `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\bench.rs:804-812`, but binary lookup is hard-coded to `workspace-root\target\release` at `:835-842`.
- **Impact:** A standard custom Cargo target directory turns a successful build into a false “binary missing” failure.
- **Concrete fix:** Resolve `CARGO_TARGET_DIR` for both operations, or force one explicit target directory. Add a custom-target-path oracle.
- **Effort:** Small, about 1–3 hours.

### Medium — ROP-BUG-CRUCIBLE-00011: oversized corpus output is buffered after rejection

- **Confidence:** High.
- **Evidence:** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\corpus.rs:482-492` records a size breach and still hashes the file. `:906-955` reads the complete file and constructs a second payload buffer.
- **Impact:** A runaway generated asset can consume unbounded memory and time after the runner already knows it violates `max_size_bytes`.
- **Concrete fix:** Stop after the size breach, or stream-parse and hash under a hard byte cap. Add an oversized sparse-file oracle that proves no full allocation.
- **Effort:** Small to medium, about 2–6 hours.

## Tracked design debt

- **ROP-REQ-CRUCIBLE-00016 — Centralize full-test run policy and subprocess execution.** One typed workspace context, stage plan, and command specification should own cwd, environment, deadlines, capture, platform launch, and report claims. This is Heavy flow because it coordinates most runner stages; individual defect fixes need not wait for the whole refactor.

## Not reported as bugs

- **Ogg header pages versus header packets — UNVERIFIED as a shipped defect.** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\corpus.rs:898-955` hashes pages after page 1, although [RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html) permits `OpusTags` to span pages. The checked-in manifest deliberately pins the narrower page-level algorithm, and this pass did not prove that current generated fixtures violate it. The semantic limitation remains in this report but did not enter the bug queue.
- **External llvm-cov filenames — UNVERIFIED.** `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\full-test\src\llvm_cov_parse.rs:140-163` does not prove workspace containment, but normal Cargo instrumentation is expected to emit workspace files. No production trigger was established.
- **IETF vector presence-only provisioning — refuted as a false-green claim.** The conformance suite consumes every `.bit` file and compares decoded output against `.dec` or `m.dec` references at `C:\worktrees\ropus\20260814-REV-ROP-CDX@CRUCIBLE-code-review-160501\tests\conformance\tests\ietf_vectors.rs:147-200`; corrupt or stale files do not pass merely because their names exist.
- **Non-root process cwd — held as conditional.** Several stages inherit the launch cwd, but the documented invocation is from the workspace through Cargo. The broader consistency concern is captured by ROP-REQ-CRUCIBLE-00016.
- **Ambisonics PASS marker followed by nonzero exit — UNVERIFIED.** The code does not require a successful exit after parsing PASS, but the current harness has no demonstrated ordinary path that prints PASS and then exits unsuccessfully.
- **Manifest path traversal and fuzz-target command injection — refuted for the reviewed threat model.** Both inputs are tracked repository configuration, not external runtime data.
- **Captured-pipe memory exhaustion — refuted.** `process_capture.rs` drains stdout and stderr concurrently and retains at most 1 MiB per stream; the confirmed problem is lifetime, not retained output size.

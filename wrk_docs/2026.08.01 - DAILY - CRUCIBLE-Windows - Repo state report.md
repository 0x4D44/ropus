## The macOS ARM workstream — the substantive new feature

Four commits, 365-line HLD, 285-line journal. Ran on an Apple Silicon Mac (`/Users/md/...`, BSD `ar`, CoreAudio, macOS `sample`), **not on CRUCIBLE**.

**Delivered:** the C reference oracle now compiles five upstream AArch64 NEON translation units on Apple Silicon; `apple-a14` set as a conservative, distributable CPU baseline; a separate Apple threshold table in `full-test`; a scalar shim working around a genuine upstream precision bug (xiph/opus#473).

**Not delivered — and this is the interesting part.** The HLD planned safe-`wide` SIMD kernels in `pitch.rs`, `fft.rs`, `mdct.rs`. All three were written, proven bit-exact, benchmarked, and **deleted**:

> CELT single/dual inner products… roughly 50% slower and lost 5/5.
> FFT downshift… roughly twice as slow and lost 5/5.
> MDCT window multiply… lost 5/5 by a wide margin.
> All three prototypes were removed.
> — `wrk_journals/2026.07.30 - JRN - macos arm optimisation.md:158-171`

Verified in the tree, not just the prose: `git diff b65f812..HEAD -- ropus/src/celt/{pitch,fft,mdct}.rs` is empty.

**Why this matters:** the retention rule (4-of-5 alternating A/B pairs, median gain above noise) was **pre-declared in the HLD before any data existed** (`HLD:154-157`). The data then went against the planned work and the work was deleted rather than rationalised. Byte-identity was proven alongside timing (same SHA-256 across both builds). A cross-family review pass caught a critical defect pre-landing — `OPUS_ARM_PRESUME_NEON` would have selected an uncompiled ARMv7 symbol.

**What it does NOT establish.** I drafted the conclusion "this answers the long-carried SIMD-beyond-`wide` backlog item" and a skeptic refuted it decisively. The backlog item is `wrk_docs/2026.04.19 - HLD - deferred-work-closeout.md:175-186`, and it proposes *hand-written* `celt/simd_neon.rs` / `celt/simd_avx2.rs` with runtime feature detection. The ARM HLD put exactly that out of scope at line 42. What was tested was *more of the already-adopted portable path*. The repo agrees with the skeptic: `ropus/README.md:160` still says "Hand-written platform intrinsics (NEON, direct AVX/AVX-512) are intentionally deferred" — at HEAD, in a paragraph the same commit edited. Nothing was measured on x86 at all, and the HLD's own decision log concedes it (`:311`).

**The correct, narrow conclusion:** on Apple AArch64, `wide::i32x4` does not pay for these three specific kernels, and one existing portable kernel already lowers to NEON (`ldp q`, `mla.4s`, `addv.4s`). The backlog item remains open and untested.

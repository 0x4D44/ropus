# HLD: macOS / ARM optimisation

**Status: SELF-APPROVED**

## Intent

Make `aarch64-apple-darwin` a first-class, measured performance target for
ropus while preserving bit-exact fixed-point behaviour and the generic
cross-platform implementation.

Success means:

1. the pinned C reference builds and runs its upstream AArch64 NEON path on
   Apple Silicon;
2. workspace-built Apple-Silicon binaries use a conservative M1-era CPU
   baseline and remain byte-identical to generic AArch64 builds;
3. Apple-Silicon profiling identifies the real codec hot paths;
4. the safe SIMD kernels retained by this change are measurably faster in
   focused measurements and do not regress the representative codec sweep;
5. focused unit, differential encode, differential decode, and round-trip
   checks pass.

## Scope

### In scope

- Architecture-aware C reference selection in `harness/build.rs`.
- Matching architecture selection in `tests/fuzz/build.rs`.
- Removal of unconditional x86 macros from the shared harness configuration.
- An exact `aarch64-apple-darwin` `apple-a14` build baseline.
- Apple-Silicon whole-codec profiling and compiler-vectorisation inspection.
- Safe `wide` implementations for the CELT inner products and FFT downshift.
- A bit-exact safe SIMD MDCT window multiply primitive and real window
  vectorisation if the focused benchmark shows a gain.
- Further FFT, band, or SILK kernels only when the profile names them and a
  safe, bit-exact implementation wins its focused benchmark.
- Durable benchmark and profiling evidence in the journal and user-facing
  build guidance where useful.

### Out of scope

- Raw `std::arch::aarch64` intrinsics or new `unsafe` in codec code.
- NE10, Accelerate/vDSP, new dependencies, feature flags, fast-math, DNN SIMD,
  or internal codec threading.
- A broad AArch64 CPU floor affecting Linux, Android, or downstream library
  builds.
- NEON rewrites of recursive or state-major SILK NSQ paths without evidence.
- Hosted CI. Validation remains local.
- Version bump, integration, push, packaging, or release.

## Current evidence

- The Apple-Silicon reference build fails in `celt/x86/x86cpu.c` because
  `harness/build.rs` unconditionally compiles x86 sources and
  `harness/config.h` unconditionally enables x86 RTCD.
- Pinned upstream commit `788cc89ce4` supplies two CELT NEON-intrinsic files,
  four SILK NEON-intrinsic files, and one fixed SILK NEON file. NE10 is a
  separate optional path and is not needed.
- `xcorr_kernel_simd` and `celt_maxabs32_simd` use `wide::i32x4`.
  `denormalise_band_simd` and `mdct_window_simd` are scalar-unrolled.
- Upstream has dedicated NEON implementations for `celt_inner_prod` and
  `dual_inner_prod`; the Rust versions remain scalar.
- A preliminary M4 whole-CLI comparison measured `apple-a14` about 2.2%
  faster than generic AArch64. `target-cpu=native` was effectively flat.
  The fixed-serial output hashes matched. This must be reproduced with the
  codec benchmark before the baseline is retained.

## Approach

### 1. Architecture-correct reference oracle

Keep common scalar C sources unchanged. Select the optimisation sources from
`CARGO_CFG_TARGET_ARCH` and `CARGO_CFG_TARGET_OS`:

- `x86` / `x86_64`: preserve the current x86 RTCD macros, x86 map sources,
  SSE/SSE2/SSE4.1 sources, and `-msse4.1`.
- `aarch64-apple-darwin`: compile these seven pinned upstream sources:
  `celt/arm/{celt_neon_intr.c,pitch_neon_intr.c}`,
  `silk/arm/{biquad_alt_neon_intr.c,LPC_inv_pred_gain_neon_intr.c,
  NSQ_del_dec_neon_intr.c,NSQ_neon.c}`, and
  `silk/fixed/arm/warped_autocorrelation_FIX_neon_intr.c`. Define
  `OPUS_ARM_MAY_HAVE_NEON_INTR`, `OPUS_ARM_PRESUME_NEON_INTR`,
  and `OPUS_ARM_PRESUME_AARCH64_NEON_INTR`. AArch64 mandates Advanced SIMD,
  so runtime NEON detection adds no value.
- other targets: compile only common scalar sources, with no architecture
  macros.

Do not define `OPUS_HAVE_RTCD` for Apple Silicon and do not compile ARM map,
`armcpu.c`, assembly, dot-product, or NE10 sources. The applicable
presumed-NEON headers dispatch directly through their `_INTR` branches.
`silk_NSQ_del_dec` is an upstream exception: its first no-RTCD branch uses
the non-intrinsic selector, so it remains scalar under this safe macro set
even though the upstream source manifest includes its NEON object. Do not
claim that every compiled object executes. In particular, do not define
non-intrinsic `OPUS_ARM_PRESUME_NEON`: it would route
`celt_pitch_xcorr` to the uncompiled ARMv7 assembly symbol
`celt_pitch_xcorr_neon`. Never define a `PRESUME_*` macro without its paired
capability and a compiled provider for every selected symbol.

Mirror the same source and macro selection in the excluded fuzz crate.
`harness-deep-plc` stays scalar because it is a separate float/DNN oracle.

Enable upstream `OPUS_CHECK_ASM` and `ENABLE_ASSERTIONS` together in the
harness's debug C build so a representative runtime compares optimised
functions with their scalar C versions and fails on a mismatch. Keep both out
of release benchmarks because check-asm intentionally repeats work. Exercise
a temporary negative control which perturbs one checked NEON result and prove
that the run aborts, then remove the perturbation. Confirm actual NEON
execution through the profiled call tree or direct call-site disassembly;
symbol presence alone is insufficient.

The ARM C oracle is not allowed to redefine ropus output. Upstream scalar/ARM
`celt_fir` saturates to `[-32767, 32767]`, while upstream x86 SSE and existing
ropus saturate to `[-32768, 32767]`. Preserve the existing portable ropus
semantics. Add an extreme-value differential case which records this known
upstream architecture difference rather than making Rust output depend on
the build host. The ARM oracle remains authoritative where upstream itself is
architecture-consistent. Audit every active fixed-point x86 override, and
investigate any new ARM differential failure rather than assuming it is this
known `celt_fir` edge.

### 2. Conservative Apple-Silicon code generation

Add:

```toml
[target.aarch64-apple-darwin]
rustflags = ["-C", "target-cpu=apple-a14"]
```

This is the conservative Rust/LLVM model available for the M1 generation.
The exact target key avoids changing other AArch64 platforms. It applies to
workspace-built binaries; published-library consumers retain control of
their final target flags.

Retain this setting only when paired `ropus-compare bench` measurements show
no representative regression and fixed-serial generic/A14 output is
identical.

### 3. Profile before broad SIMD work

Build a profiling-only release artifact with
`CARGO_PROFILE_RELEASE_STRIP=none`, keeping the release optimisation, ThinLTO,
and `.cargo/config.toml` target flags unchanged. Do not use `RUSTFLAGS` to
disable stripping because it replaces configured rustflags. Profile a
Rust-only command where possible; otherwise select the Rust time interval or
filter the call tree to Rust frames because `ropus-compare bench` runs C and
Rust sequentially. Inspect a verbose build command to confirm each artifact
received its intended `target-cpu`; the generic baseline intentionally uses
`RUSTFLAGS=-Ctarget-cpu=generic` to replace the A14 setting.

Preserve separate target directories for baseline-generic, baseline-A14,
final-generic, and final-A14 artifacts. Use five alternating A/B pairs for
each retained performance decision. Require at least four directional wins
and a median gain above the measured run-to-run noise. Report four comparisons
separately: baseline generic/A14, final generic/A14,
baseline-generic/final-generic, and each scalar/SIMD kernel. C timings are
context, not the Rust retention oracle.

Collect:

- an Instruments Time Profiler trace or, if export is unavailable, a macOS
  `sample` call tree;
- the canonical ten-vector C/Rust benchmark sweep;
- LLVM vectorisation remarks or generated AArch64 assembly for candidate
  kernels.

Profile full-band music/CELT and narrow/wide-band SILK so one content class
does not choose every optimisation.

### 4. Small safe SIMD units

Implement and measure in this order:

1. `celt_inner_prod` and `dual_inner_prod` with the existing exact
   low-16-bit multiply/wrapping-accumulate semantics.
2. FFT downshift by safely packing two `KissFftCpx` values into one `i32x4`,
   then storing fields explicitly with exact `pshr32` behaviour. Do not
   reinterpret the struct slice or rely on its layout.
3. A decomposed `mdct_window_mul_x4` primitive whose coefficient lanes are
   explicitly `i16`:

   `a * (b >> 15) + ((a * (b & 0x7fff)) >> 15)`

   with wrapping `i32` multiplication and addition matching the scalar cast.
   Document the identity
   `b = (b >> 15) * 2^15 + (b & 0x7fff)`, including negative-floor and final
   wrapping-cast semantics, and verify that `wide::i32x4` multiplication wraps
   while right shift is arithmetic. Prove it against the `i64` scalar
   implementation for every `i16` value of `a` and a small explicit
   quotient-boundary/residue set of `i32` values including
   `b >> 15 == -65536` and `65535`, plus a bounded deterministic generated
   pair set.
4. Use that primitive to replace the scalar-unrolled MDCT window loop.

Prototype, benchmark, and retain radix-4 FFT, band-energy, or SILK kernels
only when the profile shows material time there. Avoid abstraction beyond
the stable lane primitives actually shared by retained kernels.

Gate new `wide` kernels to AArch64 unless an x86 A/B measurement shows they
are neutral or faster. Non-AArch64 builds keep their existing scalar or
scalar-unrolled path, so ARM-only evidence cannot regress the calibrated
x86-64-v3 release path.

Scalar oracle functions remain under `cfg(test)`. Ignored release-mode timing
tests may print focused results, but timing never becomes a correctness
assertion.

The existing `full-test` release thresholds are calibrated on x86-64-v3 and
divide Rust time by C time. Enabling C NEON changes the Apple-Silicon
denominator, so those ratios are not comparable to the documented x86
numbers. Add and measure an AArch64 threshold table only after the oracle is
working; until then, do not treat the x86 table as an Apple-Silicon gate.

## Acceptance criteria

### Oracle and portability

- With the pinned reference present, `ropus-harness` builds natively on
  `aarch64-apple-darwin`; the pre-change x86-header failure is gone.
- The build log proves the AArch64 NEON sources compile and no x86 source
  compiles on AArch64.
- A link-producing `tests/fuzz` binary build succeeds on AArch64 with the
  same reference policy; `cargo check` alone is not sufficient.
- The x86 source selection remains present and is compile-checked where the
  local toolchain permits; other targets retain a scalar fallback.
- A debug `OPUS_CHECK_ASM=1` comparison passes, and profile or disassembly
  evidence proves a selected C NEON routine executes.
- `ENABLE_ASSERTIONS` accompanies check-asm, and a temporary negative control
  proves a checked mismatch aborts before the perturbation is removed.
- The x86 harness build and differential set run on an available x86 fleet
  host. If no host is reachable, the missing execution is recorded as an
  accepted residual risk; source selection is still cross-compiled locally.

### Exactness

- Optimised-vs-scalar kernel tests cover zero/minimum lengths, 4-lane tails,
  non-zero wrapping accumulators, high-bit truncation inputs, and
  `i32::MIN/MAX`.
- The MDCT window multiply proof test covers all 65,536 `i16` values against
  a fixed quotient-boundary/residue operand set, plus deterministic generated
  pairs.
- An extreme-value ARM `celt_fir` differential test records the known
  `-32768` x86/Rust versus `-32767` ARM/scalar saturation difference; normal
  parity cases still match.
- Every newly observed ARM differential failure is investigated against all
  active fixed-point x86 overrides before it is classified.
- Generic AArch64 and `apple-a14` fixed-serial encoded outputs are identical.
- C-vs-Rust encode bytes and C-vs-Rust decode samples pass separately for:
  8 kHz mono noise, 16 kHz mono noise, 24 kHz hybrid noise, 48 kHz stereo
  noise, and 48 kHz stereo music.
- A deterministic round trip passes.

### Performance evidence

- A symbolised Apple-Silicon profile and its top codec functions are recorded.
- Focused retained kernels win at least four of five alternating release-mode
  A/B pairs on this M4 and their median gain exceeds measured noise; rejected
  prototypes are removed.
- Repeated representative whole-codec measurements show the final tree does
  not regress the generic AArch64 baseline. Baseline/final generic/A14 results
  use isolated artifacts and are reported separately with noise and sample
  counts.
- Generated assembly or compiler remarks confirm that retained vector kernels
  emit AArch64 SIMD instructions.
- New portable `wide` kernels either keep the existing non-AArch64 path or
  also satisfy an x86 A/B retention check.
- Apple-Silicon C/Rust ratios are evaluated against measured AArch64
  thresholds, never the x86-64-v3 table.

### Quality

- `cargo fmt --check` passes.
- Focused clippy/build/tests for touched packages pass without new warnings.
- The code-reviewer apply pass and a final simplicity pass leave no unresolved
  correctness finding.
- The worktree ends clean with atomic commits and no version bump.

## Decision log

| Decision | Reason |
|---|---|
| Use `apple-a14`, not `native`. | Conservative M1-era floor; preliminary M4 evidence favours it and `native` is not distributable. |
| Presume NEON only in the C AArch64 oracle. | Advanced SIMD is architectural on AArch64; no runtime dispatch is required. |
| Keep existing ropus saturation output portable. | Upstream ARM scalar and x86 SSE disagree at one `celt_fir` extreme; host-dependent Rust output would be a regression. |
| Keep Rust SIMD portable through `wide`. | Repository policy forbids new codec `unsafe`; current dependency already provides a safe NEON backend. |
| Gate new kernels to AArch64 by default. | ARM-only measurements cannot justify changing the calibrated x86 code path. |
| No new benchmark dependency. | Existing codec bench, macOS profiling tools, `Instant`, and `black_box` are sufficient. |
| Retain only measured candidate kernels. | SIMD-looking code can be slower after packing, gathers, and horizontal reduction. |
| Keep performance as evidence, not a flaky test gate. | Timing noise must not turn correctness validation intermittent. |
| Leave `tests/harness/config.h` alone. | It is an unused legacy copy; changing dead code does not advance the task. |

## Review record

### Adversarial review

Two independent reviewers inspected the design, then each checked the
other's findings. All checks ran; no finding is unverified.

Surviving findings folded into this design:

- restrict presumed NEON to macOS AArch64 and enumerate the exact upstream
  macros, source files, and exclusions;
- require link-level fuzz validation, non-vacuous `OPUS_CHECK_ASM`, and
  execution evidence rather than object presence;
- preserve ropus's deliberate x86-compatible `celt_fir` saturation and expose
  the known ARM/scalar edge explicitly;
- use safe explicit `KissFftCpx` packing, exact arithmetic proof cases,
  symbol-preserving profiling, isolated artifacts, and a predeclared paired
  performance rule.

### Cross-family review

Claude Opus completed one read-only pass. It found one critical issue:
`OPUS_ARM_PRESUME_NEON` would select an uncompiled ARMv7
`celt_pitch_xcorr_neon` symbol. The macro was removed. The required targeted
re-review confirmed the critical issue is resolved and that the three
`_NEON_INTR` macros select compiled providers. It also identified the scalar
`silk_NSQ_del_dec` exception now documented above.

Other useful items folded in:

- pair `ENABLE_ASSERTIONS` with check-asm and prove it with a negative
  control;
- keep unmeasured new `wide` paths off x86, and separate ARM benchmark
  thresholds because C NEON changes the timing denominator;
- preserve configured CPU flags when stripping is disabled and verify rustc
  commands;
- make missing x86-host execution an explicit residual risk;
- narrow the MDCT multiply contract to `i16` coefficient lanes and spell out
  wrapping semantics;
- correct the stale SIMD feature comment while editing that module.

Rejected: changing or deleting `tests/harness/config.h`; it is dead legacy
code and touching it would add no validation or shipped value.
